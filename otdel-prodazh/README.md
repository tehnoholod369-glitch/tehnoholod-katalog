# ИИ-отдел продаж ИП «ТехноХолод»

Каркас отдела продаж из ИИ-экспертов: обращение приходит в одну точку, эксперт по своему
направлению подбирает оборудование по фактическому каталогу, расчётчик считает деньги,
начальник отдела сводит всё в отчёты, просьбы и предложения владельцу.

Версия каркаса — **v0.1, 22.08.2026**. Работает в текущем виде, но регламент подбора
и часть констант ждут утверждения владельцем — см. раздел «Что решить владельцу».

---

## Главная мысль: не чат-бот, а конвейер с общей памятью

Соблазн — сделать «умного продавца-бота». Это тупик: каждый разговор начинается с нуля,
свести ничего нельзя, отчёт взять неоткуда, а цену модель называет по памяти.

Отдел продаж отличается от чата тремя вещами, и все три здесь заложены в конструкцию:

1. **Разделение труда.** Один эксперт на направление, а не один агент на всё. Промах в
   подборе полупрома и в подборе радиатора лечится разными знаниями.
2. **Общая память.** Реестр сделок переживает конец сессии. Без него отдела нет — есть
   набор одноразовых разговоров.
3. **Один сводящий.** Информация стекается к начальнику отдела, и только он говорит с
   владельцем. Владелец читает одну сводку, а не семь агентов.

И одно правило поверх всего, из свода 4П: **эксперт не вспоминает цену — он её находит.**
Ассортимент и цены берутся запросом к каталогу. Нет позиции в выдаче — значит её нет,
и это ответ «нет данных», а не повод предложить модель по памяти.

## Схема

```
   WhatsApp · сайт · omarket.kz · почта · звонок
                      │
                      ▼
            ┌───────────────────┐
            │    ДИСПЕТЧЕР      │  принимает, квалифицирует, заводит сделку
            └─────────┬─────────┘  и маршрутизирует по направлению
                      │
      ┌───────────┬───┴───────┬───────────┬────────────┐
      ▼           ▼           ▼           ▼            ▼
 ┌─────────┐ ┌─────────┐ ┌─────────┐ ┌─────────┐ ┌──────────┐
 │  СПЛИТ  │ │ПОЛУПРОМ │ │ВЕНТИЛЯ- │ │ОТОПЛЕ-  │ │ВОДОНАГРЕВ│   эксперты подбора
 │ бытовые │ │  VRF    │ │  ЦИЯ    │ │  НИЕ    │ │и водоочис│
 └────┬────┘ └────┬────┘ └────┬────┘ └────┬────┘ └────┬─────┘
      └───────────┴───────┬───┴───────────┴───────────┘
                          ▼
                  ┌───────────────┐
                  │  РАСЧЁТЧИК    │  цена клиенту, НДС, монтаж, КП
                  └───────┬───────┘
                          ▼
              ╔═══════════════════════╗
              ║  РЕЕСТР СДЕЛОК        ║  ledger/events.jsonl — только дозапись
              ║  общая память отдела  ║  все пишут сюда, никто не пишет мимо
              ╚═══════════╤═══════════╝
                          ▼
              ┌───────────────────────┐
              │ НАЧАЛЬНИК ОТДЕЛА      │  единственный, кто говорит с владельцем
              │ ПРОДАЖ                │  отчёты · просьбы · предложения
              └───────────┬───────────┘
                          ▼
                      ВЛАДЕЛЕЦ
```

Ключевое в схеме — **не стрелки между агентами, а квадрат посередине**. Эксперты не
пересказывают друг другу результаты. Каждый пишет структурное событие в реестр, начальник
читает реестр. Поэтому агента можно добавить, заменить или временно выключить, и остальные
этого не заметят — на этом держится расширяемость.

## Роли

Определения агентов лежат в `.claude/agents/`. Каждый — отдельный файл, добавить новое
направление = добавить файл.

| Роль | Файл | Отвечает за |
|---|---|---|
| Диспетчер | `dispetcher.md` | Принять обращение, вытащить объект/задачу/сроки/бюджет, завести сделку, выбрать эксперта |
| Эксперт: бытовой климат | `ekspert-split.md` | Бытовые сплиты, мультисплит, мобильные |
| Эксперт: полупром и промышленный холод | `ekspert-poluprom.md` | Полупром, мини-VRF, чиллеры, фанкойлы, прецизионные, воздухоохладители |
| Эксперт: вентиляция | `ekspert-ventilyaciya.md` | Вентиляция, промвентиляторы, рекуператоры, осушители |
| Эксперт: отопление | `ekspert-otoplenie.md` | Радиаторы, камины, обогреватели, ИК, пушки, завесы, тепловые насосы, водяные тепловентиляторы |
| Эксперт: водонагрев и водоочистка | `ekspert-vodonagrev.md` | Водонагреватели, водоочистка |
| Расчётчик | `raschetchik.md` | Цена клиенту, наценка, НДС, монтаж, рассрочка, сборка КП |
| Начальник отдела продаж | `nachalnik-otdela-prodazh.md` | Сводит реестр в отчёт, просьбы и предложения. Только он обращается к владельцу |

Пять экспертов на 24 группы техники — сознательный выбор. Дробить по одному агенту на
группу рано: определения расползутся, а знания в них будут повторяться. Признак, что пора
делить, — эксперту регулярно не хватает контекста внутри его направления.

## Путь одного обращения

1. Пришло обращение → **диспетчер** заводит сделку:
   `ledger.py lead --source whatsapp --client … --need "…"` → выдан `D-ГГГГММДД-NNN`.
2. Диспетчер определяет направление и вызывает нужного **эксперта**.
3. Эксперт ищет по каталогу: `catalog.py find --group … --area … --instock`.
   Предлагает 2–3 варианта: рабочий, дешевле, лучше. Пишет
   `ledger.py podbor --deal … --sku … --text "обоснование"`.
   Не нашёл подходящего → `ledger.py probel --chto "…"` вместо выдумки.
4. **Расчётчик** считает цену клиенту, монтаж и НДС, собирает КП (навык `kp-generator`),
   пишет `ledger.py kp --deal … --summa …`.
5. Ответ собирается по форме из навыка `otdel-prodazh` и **отправляется человеком**.
   Факт отправки пишется: `ledger.py otpravleno --deal … [--pravki "что исправили"]`.
   Доля ответов без правок — главная метрика качества ролей.
6. Дальше сделка двигается по этапам: `ledger.py stage --deal … --to торг`.
7. **Начальник отдела** раз в день собирает `ledger.py report --period day`, добавляет
   разбор и кладёт в `otdel-prodazh/otchety/`.

Этапы сделки: `новый → квалификация → подбор → кп → торг → выигран | проигран | отложен`.
Закрыть сделку без причины (`--why`) нельзя: причины проигрышей — половина пользы отчёта.

## Инструменты

Оба — обычные скрипты, работают и без ИИ. Это специально: агент, у которого инструмент
детерминированный, ошибается на порядок реже, чем агент, который «помнит».

### `tools/catalog.py` — поиск по каталогу

Индекс собран из `katalog-*.html` этого репозитория: **3 083 позиции, 24 группы, 1 640 в
наличии** (22.08.2026). Витрина собирается пайплайном из мастер-таблицы PIM, поэтому индекс
здесь — производная витрины, а не второй источник правды.

Индекс **в git не хранится и пересобирается сам**, как только страницы каталога оказались
новее его. Это снимает самый дорогой сбой отдела — продажу по ценам прошлой сборки: забыть
про обновление физически не получится, потому что помнить нечего.

```bash
python3 tools/catalog.py build                                   # пересобрать вручную
python3 tools/catalog.py find --group bytovye --area 25 --instock --limit 5
python3 tools/catalog.py find --q кассетный --price-max 900000 --instock
python3 tools/catalog.py show bytovye:DTXS-09K3XA41A             # полные ТТХ
python3 tools/catalog.py groups                                  # группы и количества
python3 tools/catalog.py doctor                                  # дыры и противоречия витрины
```

Почему это важнее, чем кажется: каталог теперь машиночитаем **из git**, без машины
владельца и без подключённой папки PIM. Значит эксперт работает из любой сессии — с
телефона, из веб-Claude, из будущей интеграции с WhatsApp.

### `tools/kp_blank.py` — бланк коммерческого предложения

Оформление, а не расчёт: деньги берутся из `kp_calc.py` навыка `kp-generator`, здесь
раскладка по бланку — логотип, реквизиты, условия, подписи. Отдаёт `.html` (печатать в PDF
из браузера) и `.txt` для WhatsApp, кладёт в `<данные отдела>/kp/`.

Цены работ — `otdel-prodazh/prays-montazha.json`. Файл разбит на разделы по группам
техники, у каждого флаг `utverzhdeno`. Утверждённый раздел `kp-json` подставляет по
`--montazh N --gruppa-rabot <раздел>`; неутверждённый **не подставит** и скажет, что там
лежит только предложение по рынку — цену работ нельзя выставить клиенту, пока владелец её
не решил.

Утверждено 23.08.2026: **сплиты** — монтаж 50 000 ₸ с трассой 4 м в комплекте, кронштейн
6 500 ₸ на блок, трасса сверх 4 м 9 000 ₸/м ставкой по замеру. **Выезд** — до 30 км от
базы на Казыбаева включён, 30–60 км 20 000 ₸, 60–100 км 40 000 ₸, дальше отдельно;
подставляется по `--km`, один раз на адрес.

Ждут решения владельца: полупром, мультисплит, водонагреватели, радиаторы, тепловые
завесы, вентиляция, рекуператоры. Группы без монтажа и группы «только по проекту»
перечислены там же.

Реквизиты и типовые условия — `otdel-prodazh/rekvizity.json`. Утверждено 23.08.2026:
телефон в документах `+7 700 036 93 69`, срок действия КП 7 дней, номер КП = номер сделки,
гарантия разведена на производителя и на монтаж. Порядок оплаты и срок поставки
заполнены решениями владельца от того же числа.

### `tools/svodka.sh` · `tools/svodka.cmd` — сводка по расписанию

Запуск начальника отдела продаж без человека: собирает документ за вчера и кладёт в
`otdel-prodazh/otchety/ГГГГ-ММ-ДД.md`. Ставится в планировщик на будни, на утро.

Работает только там, где лежит журнал, — то есть на машине владельца. В облачной сессии
и на чужом клоне журнала нет, и сводка выйдет по пустому файлу. Права у запуска узкие:
чтение журнала и каталога, запись отчёта, ничего больше.

### `tools/ledger.py` — реестр сделок

Журнал событий, только дозапись: `otdel-prodazh/ledger/events.jsonl`. Состояние сделки
не хранится, а вычисляется проигрыванием событий — рассинхронизировать нечего, любую
цифру в отчёте можно проследить до строки журнала.

**Журнал в этот репозиторий не попадает.** Он публичный — его отдаёт jsDelivr, так
витрина получает фотографии. В событии `lead` лежат имя клиента, телефон, адрес объекта и
текст обращения дословно; публиковать это нельзя. То же у отчётов и разборов обращений.

Где данные лежат на самом деле — говорит сам инструмент:

```bash
python3 tools/ledger.py gde
```

Порядок поиска: переменная `TEHNOHOLOD_OTDEL` → соседний приватный репозиторий
`../tehnoholod-otdel-prodazh` → папка `otdel-prodazh` этого репозитория. Последний вариант
рабочий, но у него нет ни бэкапа, ни доступа из облачной сессии. Переезд на первый —
одна команда, план показывается до записи:

```bash
python3 tools/pereezd-otdela.py            # что и куда поедет
python3 tools/pereezd-otdela.py --sdelat   # выполнить: перенести, git init, коммит
python3 tools/pereezd-otdela.py --push https://github.com/<логин>/tehnoholod-otdel-prodazh.git
python3 tools/pereezd-otdela.py --arhiv otdel.zip   # упаковать данные
```

Репозиторий на GitHub скрипт не создаёт — это делает владелец учётной записи, и правильно,
что не может никто другой. `--push` привязывает уже созданный и отправляет.

`--arhiv` нужен, пока репозитория нет: журнал существует в одном экземпляре, и вместе с
диском умирает история всех сделок. В архиве персональные данные клиентов — в публичные
места не класть.

```bash
python3 tools/ledger.py lead --by dispetcher --source whatsapp \
    --client "Айгуль Т." --contact "+7 701 …" --city Алматы \
    --need "кондиционер в спальню 18 м², тихий, с обогревом" --budget 250000
python3 tools/ledger.py podbor --deal D-20260822-001 --by ekspert-split \
    --sku bytovye:DTXS-09K3XA41A --text "9000 BTU при 18 м², запас на южную сторону"
python3 tools/ledger.py kp-json --deal D-20260822-001 --pos "bytovye:DTXS-09K3XA41A=1" \
    --rabota "Монтаж сплит-системы, базовый комплект=45000" --out kp.json
python3 tools/ledger.py kp --deal D-20260822-001 --by raschetchik --summa 268000
python3 tools/ledger.py stage --deal D-20260822-001 --to выигран --why "цена и срок монтажа"
python3 tools/ledger.py report --period week
```

`kp-json` — мост к навыку `kp-generator`, а не второй генератор КП: собирает его входной
контракт, подставляя названия и цены из каталога, заказчика и объект из события `lead`.
Руками задаются только работы — монтажа и выезда в каталоге нет. Считает деньги и оформляет
документ всё равно `kp-generator`: два генератора неизбежно разойдутся в НДС.

Защиты в реестре стоят там, где ИИ обычно врёт: подбор с несуществующим SKU не запишется
(проверка по индексу каталога), закрытие сделки без причины не запишется, «нет подходящего»
пишется отдельным типом события, а не пустым подбором.

## Как запустить сегодня

Каркас работает там же, где вы уже работаете, — в сессии Claude Code с этим репозиторием.

0. **До первых настоящих клиентов** — пройти приёмку по `priyomka.md`: 15–20 реальных
   прошлых обращений прогоняются через отдел, сверяется, где он врёт. Один вечер работы,
   и он окупается: у ИИ-агента нет испытательного срока, он с первого дня работает ровно
   так, как написано в его определении.
1. Ничего не настраивать: индекс соберётся сам при первом обращении к каталогу.
2. Обращение от клиента отдаёте сессии. Она играет приёмную: заводит сделку и вызывает
   нужного агента из `.claude/agents/`.
3. В конце дня: «сводка по отделу продаж» → начальник отдела соберёт отчёт.

Ограничение текущего слоя, которое надо знать: **агент не может вызвать другого агента**.
Поэтому маршрутизирует главная сессия, а не диспетчер сам по себе. Для человека это
незаметно, для проектирования важно: цепочки строятся из главной сессии, а не внутри агента.

Дальнейшие шаги автоматизации — `ROADMAP.md`. Коротко: расписание для ежедневной сводки,
приём заявок из WhatsApp через Make.com, затем headless-режим на Claude Agent SDK.

## Что решить владельцу

**Решено 23.08.2026 — НДС.** Все прайсы и цены каталога идут **с НДС**. Сверху 16 % не
начисляется, налог выделяется из суммы: `НДС = итог × 16 ÷ 116`. В КП пишется «в том числе
НДС 16 %». Зафиксировано в `raschetchik.md`.

⚠️ Отсюда вылезает противоречие, которое надо снять отдельно: навык `omarket-cp-excel`
считает цену предложения по правилу `дилерская × 1,25 × 1,16`. Если дилерские прайсы уже с
НДС, этот множитель 1,16 начисляет налог второй раз, и цена на omarket завышена на шестую
часть. Каркас отдела продаж это правило не трогает — но проверить его стоит.

Остальные открытые пункты:

1. **Регламент подбора** (`reglament-podbora.md`) — шкала «площадь → мощность» снята с
   фактического каталога, но поправки (южная сторона, остекление, техника, люди) — черновик.
   Нужно утвердить или заменить своими.
2. **Стоимость монтажа** — в каркасе её нет: в каталоге монтажа нет, а придумывать цену
   нельзя. Нужен прайс монтажа, иначе КП всегда будет с пустой строкой.
3. **Кто отвечает клиенту** — сейчас ответ готовит система, отправляет человек. Момент,
   когда ИИ начнёт отвечать клиенту напрямую, стоит выбрать отдельно и осознанно.
4. **Найдено при сборке индекса, к правке в PIM:** у 39 бытовых карточек числовое поле
   площади на витрине втрое больше паспортного (FUNAI, ROYAL CLIMA — похоже, в поле попал
   объём в м³). Клиенту в названии и ТТХ показано верное значение, но фильтр и сортировка
   «по площади» на сайте по этим позициям врут. Подбор здесь опирается на ТТХ, расхождение
   помечается. Полный список: `python3 tools/catalog.py doctor --limit 50`.

## Границы

Каркас не заменяет мастер-таблицу, не правит цены и не публикует сайт — для этого есть
