# Порядок роста и автоматизации

Порядок фаз выбран по правилу «Прагматично»: сначала дешёвое с большой отдачей. Каждая
фаза даёт работающий результат сама по себе — если следующую не делать, предыдущая не
рассыпается.

---

## Фаза 1 — каркас. Сделано 22.08.2026

- Каталог стал машиночитаемым из git: `tools/catalog.py`, 3 083 позиции, 24 группы.
  Экспертам больше не нужна машина владельца и подключённая папка PIM.
- Реестр сделок: `tools/ledger.py`, журнал событий с дозаписью.
- Восемь ролей в `.claude/agents/`, общий регламент подбора, контракты данных.
- Проверка витрины `catalog.py doctor` — сырьё для предложений владельцу.

**Что это уже даёт.** Подбор перестал зависеть от памяти модели: цена и наличие берутся
запросом. Сделки перестали теряться между сессиями. У владельца появился один источник
сводки вместо семи разговоров.

**Чего пока нет.** Всё запускается руками из сессии, обращения заводятся вручную,
сводка собирается по просьбе.

## Фаза 2 — снять ручной запуск. Часы работы

1. **Прогрев индекса.** Индекс уже пересобирается сам, когда страницы каталога новее его,
   так что продажа по ценам прошлой сборки исключена конструкцией. Остаётся мелочь: добавить
   `python3 tools/catalog.py build` в конец `ОБНОВИТЬ-ВСЁ.py`, чтобы первый за день запрос
   эксперта не ждал пересборки.
2. **Ежедневная сводка по расписанию.** Задача на будни, утром: «собери сводку отдела
   продаж за вчера, положи в `otdel-prodazh/otchety/`». В Claude Code это Routine
   (`create_trigger`), на машине владельца — планировщик задач.
3. **Папка отчётов** `otdel-prodazh/otchety/ГГГГ-ММ-ДД.md` — история решений, а не только
   последняя картинка.

Отдача: владелец начинает получать сводку, ничего не запрашивая. Это тот момент, когда
отдел начинает работать без напоминаний.

## Фаза 3 — приём заявок без человека. Дни работы

Сейчас самое узкое место — обращение попадает в реестр, только если его туда занесли.
Каналы подключаются по одному, в порядке отдачи:

| Канал | Как | Что даёт |
|---|---|---|
| **WhatsApp** | Make.com уже используется для сервис-карты 369 — сценарий кладёт входящее сообщение в очередь заявок, диспетчер разбирает | Основной поток обращений |
| **omarket.kz** | Навык `omarket-monitor` уже снимает планируемые закупки — его выдача становится событиями `lead` | Тендеры перестают теряться |
| **Почта** | Коннектор Gmail: письма с запросом цены → `lead` | Юрлица пишут почтой |
| **Сайт** | Форма заявки складывает обращение в тот же формат | Заявки с витрины |

Правило подключения: канал не «интегрируется» с ИИ, а кладёт обращение в **тот же формат
события `lead`**. Тогда пятый канал стоит столько же, сколько второй. Как только каждый
канал начнёт носить свой формат, отдел встанет.

Отдача: воронка становится полной. До этого момента любая аналитика по конверсии считается
по тому, что вспомнили занести, — то есть неверна.

## Фаза 4 — первый ответ клиенту круглосуточно. Недели работы

Технически: Claude Agent SDK, headless-процесс с теми же определениями ролей и теми же
инструментами. Определения агентов из `.claude/agents/` переносить не придётся — они уже
не привязаны к интерфейсу.

Порядок ввода, от безопасного к смелому:

1. Система **готовит** ответ, отправляет человек. Считаем долю ответов, ушедших без правок.
2. Доля стабильно высокая → система **отвечает сама на типовое** (есть ли в наличии,
   сколько стоит, какая площадь) и передаёт человеку всё остальное.
3. Подбор и КП **всегда** остаются с подтверждением человека. Ошибка в подборе стоит
   выезда монтажной бригады, а не извинения в переписке.

Не начинать эту фазу раньше третьей: круглосуточный ответ по неполной воронке даёт
быстрый неправильный ответ вместо медленного правильного.

## Фаза 5 — отдел начинает влиять на закупку. Постоянно

Когда в журнале накопятся сотни сделок, из него считается то, чего сегодня взять неоткуда:

- конверсия по источникам — куда имеет смысл вкладывать;
- конверсия по направлениям и брендам — что продаётся, а что лежит;
- причины проигрышей группами — цена, срок, отсутствие позиции, монтаж;
- **события `probel`** — спрос, которого нет в ассортименте. Прямая заявка на заведение
  позиции, подкреплённая числом обращений, а не ощущением;
- сделки, зависшие на этапе, — где именно теряется клиент.

Отсюда предложения начальника отдела перестают быть текстом и становятся счётом:
«кассетный 10 кВт спрашивали 7 раз за месяц, суммарно на 4,2 млн ₸, в каталоге нет».

## Когда заводить нового ИИ-эксперта

Не «по группе техники», а по признакам:

- эксперту регулярно не хватает контекста внутри направления — определение раздулось,
  правила соседних групп мешают друг другу;
- у направления появились свои правила подбора, которые никому больше не нужны;
- появилось новое направление продаж (проектирование, сервис, запчасти);
- по журналу видно, что качество подбора в одной группе устойчиво хуже остальных.

Не признак: «групп техники стало больше». Пять экспертов спокойно держат 24 группы.

## Чего не делать

Ошибки, которые сломают конструкцию, — они дешевле в предотвращении, чем в разборе:

1. **Не давать агентам править мастер-таблицу.** Отдел продаж читает данные. Правит их
   пайплайн PIM. Иначе через месяц никто не скажет, откуда взялась цена.
2. **Не заводить второй реестр.** Ни таблицы в Google Sheets «для удобства», ни списка в
   заметках. Один журнал. Второй источник правды — конец сводимости.
3. **Не давать эксперту отвечать клиенту в обход реестра.** Ответ, которого нет в журнале,
   для отчёта не существует.
4. **Не разрешать «примерно похожую» модель.** Нет позиции — это `probel`. Ровно этот
   компромисс превращает подбор в лотерею.
5. **Не автоматизировать редкое.** Разовая задача делается руками. Автоматизируется то,
   что повторяется каждую неделю.
