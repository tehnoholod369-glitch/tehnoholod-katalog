# Контракты данных отдела продаж

Договорённость о форме данных, которыми обмениваются роли. Пока контракт один и
соблюдается агентами, отдел можно расширять: новый эксперт встраивается, если умеет
писать те же события.

Физически всё лежит в `otdel-prodazh/ledger/events.jsonl` — одна строка JSON на событие,
только дозапись. Писать напрямую нельзя, только через `tools/ledger.py`: он проставляет
время, присваивает номера и не пропускает заведомо мусорные записи.

Этот файл **в git не попадает** и попадать не должен: репозиторий каталога публичный, а в
`lead` лежат имя клиента, контакт и адрес объекта. В репозитории хранится только заготовка
`events.jsonl.primer`. Значит, журнал существует ровно в одном экземпляре — на машине
владельца, и бэкап у него общий с мастер-таблицей PIM.

---

## Общие поля

| Поле | Тип | Смысл |
|---|---|---|
| `ts` | строка ISO 8601 с зоной +05:00 | Момент записи. Проставляется инструментом |
| `type` | строка | Тип события, список ниже |
| `deal` | `D-ГГГГММДД-NNN` | Сделка. У `vopros` и `probel` может отсутствовать |
| `by` | строка | Кто записал: имя роли (`ekspert-split`) или человек |

Время — Алматы, UTC+5. Казахстан живёт в одном часовом поясе с 01.03.2024.

## Типы событий

### `lead` — обращение принято

| Поле | Обязательно | Смысл |
|---|---|---|
| `client` | нет | Имя или название организации |
| `contact` | нет | Телефон, WhatsApp, почта |
| `source` | нет | `whatsapp` · `сайт` · `omarket` · `почта` · `звонок` · `рекомендация` |
| `city` | нет | Город и район объекта |
| `need` | **да** | Задача словами клиента, не пересказом |
| `budget` | нет | Число в тенге, если названо |

`need` пишется словами клиента специально: пересказ теряет то, за что потом цепляется
разбор проигранной сделки.

### `podbor` — эксперт подобрал оборудование

| Поле | Обязательно | Смысл |
|---|---|---|
| `skus` | **да** | Список ID каталога, минимум один |
| `text` | нет | Обоснование: почему эти, что проверено, что осталось неизвестным |
| `vne_kataloga` | авто | SKU, которых нет в индексе — заполняется при `--force` |

Каждый SKU сверяется с `data/catalog-index.json`. Несуществующий не запишется без
явного `--force`. Подбор без единого SKU не записывается вообще: «ничего не подошло» —
это событие `probel`, а не пустой подбор.

### `kp` — коммерческое предложение выставлено

| Поле | Обязательно | Смысл |
|---|---|---|
| `summa` | **да** | Итог КП с НДС, тенге |
| `nds` | нет | Сумма НДС в составе итога |
| `montazh` | нет | Монтаж в составе итога |
| `fajl` | нет | Путь или ссылка на файл КП |

Само КП собирает навык `kp-generator`. Вход для него готовит `ledger.py kp-json`: он
берёт названия и цены из каталога, заказчика и объект из `lead`, а руками принимает только
работы, которых в каталоге нет. Своего расчёта КП в отделе нет намеренно — второй счётчик
НДС разойдётся с первым в первый же месяц.

### `stage` — смена этапа

| Поле | Обязательно | Смысл |
|---|---|---|
| `to` | **да** | `новый` · `квалификация` · `подбор` · `кп` · `торг` · `выигран` · `проигран` · `отложен` |
| `why` | при `выигран`/`проигран` | Причина. Без неё закрытие не записывается |

Этапы `подбор` и `кп` проставляются сами при соответствующих событиях — руками их
двигать не нужно.

### `vopros` / `otvet` — что решает владелец

| Поле | Обязательно | Смысл |
|---|---|---|
| `id` | авто | `Q-NNN`, присваивается инструментом |
| `text` | **да** | Вопрос одной фразой, с контекстом внутри |
| `srochno` | нет | Флаг для верха сводки |

Ответ владельца пишется событием `otvet` с полем `vopros: "Q-NNN"`. Вопрос без ответа
попадает в каждую сводку, пока на него не ответят, — механизм намеренно назойливый.

### `probel` — просили, а в каталоге нет

| Поле | Обязательно | Смысл |
|---|---|---|
| `chto` | **да** | Чего не хватило. Формулировка одинаковая от раза к разу |
| `gruppa` | нет | Slug группы техники |
| `text` | нет | Подробности запроса |

Это самое ценное событие для развития ассортимента: показывает спрос, которого нет в
продажах, — по нему не сделать выводов ни по одному другому источнику.

### `otpravleno` — ответ ушёл клиенту

| Поле | Обязательно | Смысл |
|---|---|---|
| `kanal` | нет | `whatsapp` · `почта` · `звонок` |
| `chto` | нет | О чём был ответ: подбор, цена, наличие, срок |
| `pravki` | нет | **Что человек исправил перед отправкой.** Пусто = ушло как есть |

Отвечает клиенту человек, поэтому это событие — единственное место, где видно, насколько
система попадает. Доля ответов без правок считается в сводке и служит мерой готовности
отдела к следующему шагу самостоятельности. Повторяющаяся правка — не случайность, а
строчка, которой не хватает в регламенте или в определении роли.

### `zametka` — свободная запись в историю сделки

Всё, что не укладывается в типы выше: договорённость по срокам, содержание звонка,
обещание перезвонить.

## Что читает начальник отдела

Начальник **не пересчитывает работу экспертов и не ходит в каталог за ценами**. Он
работает с двумя выдачами:

```bash
python3 tools/ledger.py report --period day --json    # цифры и списки
python3 tools/catalog.py doctor --json                # состояние витрины
```

Разделение жёсткое: цифры даёт инструмент, смысл — начальник. Если в отчёте появилось
число, которого нет в выдаче инструмента, отчёт неверен независимо от того, насколько
число правдоподобно.

## Добавление новой роли

1. Файл в `.claude/agents/`, описание — когда вызывать, а не только что делает.
2. Диапазон групп техники — из `python3 tools/catalog.py groups`, без пересечений с
   действующими экспертами.
3. Пишет те же события. Новый тип события заводится только вместе с правкой `ledger.py`
   и этого файла — иначе отчёт его не увидит и работа роли пропадёт.
4. Строка в таблице ролей `README.md`.
